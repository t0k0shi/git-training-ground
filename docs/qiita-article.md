# 「はじめてのPR」を気軽に試せるOSSを作りました

## きっかけ

コードを書く人が、ここ数年でずいぶん増えました。GitHub の年次レポート「Octoverse 2025」によると、GitHub の開発者は1億8,000万人を超え、日本の開発者も2020年から2025年で3倍以上になりました。

生成AIで書き始める人も増えています。同じレポートでは、新しく GitHub に来た開発者の約8割が、最初の1週間で AI のコーディング支援を使っていました。AI に頼めば、プログラミングを本格的に学んでいない人でも、動くコードが手に入る時代になっています。

ただ、AI は一度にたくさんのファイルを書き換えるので、どこが変わったのかを人が確かめて、まずければ前の状態に戻せるようにしておかなければいけません。その土台になるのが Git です。AI が書くコードが増えるほど、変更を管理する力の重みは増していると感じています。

AI が書いた変更をチームのコードに取り込むときも、ブランチ（本流から分けた作業用の枝）を切って PR（プルリクエスト。自分の変更を取り込んでほしいと依頼する機能）を出し、レビューを受けてからマージ（取り込み）する流れは変わりません。ところが、AI に頼んでコードを書き始めた人の中には、ブランチや PR の操作を誰にも教わらないままの人もいると思います。その割に、ブラウザだけで PR の流れを試せて、間違いを日本語で返してくれる練習場は、あまり見かけません。そこで、失敗しても誰も困らない練習場を作りました。

リポジトリ: https://github.com/t0k0shi/git-training-ground

![トップページのスクリーンショット](top.png)

やることは簡単です。JSON ファイルに自分の情報を足して PR を送ります。マージされたら、トップページに自分のカードが出ます。それだけです。編集を JSON 1ファイルに絞ったのは、コードの中身ではなく、PR の流れそのものに集中してほしかったからです。手順は[チュートリアル](https://t0k0shi.github.io/git-training-ground/tutorial)に9ステップでまとめました。

英語圏には、first-contributions という定番の練習リポジトリがあります。スターが5万以上あり、日本語の手順書もあります。ただ、手順はリポジトリを手元のパソコンに複製（clone）して、コマンドラインで名前を書き足すのが基本です。この練習場では、ブラウザだけで完結する画面付きの手順と、間違いを日本語で返す自動チェックを用意しました。マージされると、自分のカードがサイトに表示されるのも違いです。

## OSS の最初の一歩は、なぜ怖いのか

PR の流れを、知らない人のリポジトリで初めて体験する場が OSS です。OSS コントリビューションの体験記を読むと、だいたい同じ悩みが出てきます。

> OSSは「凄腕の人たちだけが触る神聖な場所」だと思っていた
> ― [OSSコントリビュートに挑戦してみた](https://zenn.dev/loglass/articles/aaca355c10c673)

> 通常開発とOSS開発では求められる基準が違う。「頭がちぎれるくらい考える」必要がある
> ― [OSS活動で3ヶ月で学んだこと](https://qiita.com/YmBIgo/items/a7c42042f7e7d7c49d98)

練習場では、こうした悩みにそれぞれ次のように手を打ちました。

| 障壁 | よくある声 | この練習場での対策 |
|------|-----------|------------------|
| 心理的 | 「自分には無理」「すごい人の世界」「変なコードを送ったら怒られそう」 | 練習用なので、失敗して OK |
| 技術的 | 「知らないコードのどこから手をつければいいのか」「PR の作り方がわからない」 | 編集するのは JSON 1ファイルだけ |
| 品質 | 「普段の仕事より高い基準を求められそう」 | 自動のチェックが、間違いを日本語で教えてくれる |
| 英語 | 「読むのも書くのもしんどい」 | すべて日本語 |

体験記を読んでいると、踏み出してしまえば意外となんとかなった、という印象も受けました。

**でも、最初の一歩が怖いんです。**

人のダッシュボードのような画面を開いて、Fork ボタンを押す。「これでいいのかな」と思いながら push する。そもそも、元のコードを壊さないかも心配です。初めては、誰だって怖いと思います。実験できて、失敗しても許される場所が、自分は欲しかったんです。

マージされたらトップページに自分のカードが出るのは、その一歩へのちょっとしたご褒美です。

## 機能

### チュートリアル

<!-- 画像: チュートリアルページ（v5）のスクリーンショットをアップロードして差し替える -->
![チュートリアルページ](tutorial.png)

元のリポジトリを自分のアカウントに複製する「Fork」から、PR の作成までを、9ステップで説明しています。各ステップには、その操作が「なぜ」必要かも書きました。コピーボタン付きのコードブロックと、FAQ 10問も添えています。

<!-- 画像: public/tutorial/step4-after-paste.png をアップロードして差し替える -->
![チュートリアルの画像の例（コードを貼り付けた後のエディタ）](step4-after-paste.png)

各ステップには、実際の GitHub の画面を12枚載せ、押す場所は赤枠で囲みました。GitHub の画面は時々変わるので、手で撮り直していては続きません。ブラウザを自動で操作できる Playwright で GitHub を操作して撮るスクリプトを書き、赤枠とアバターのぼかしも自動で入れるようにしました。ログインが必要な画面は、撮影用のサブアカウントで撮っています。

### 貢献者カード

```json
{
  "name": "あなたの名前",
  "github": "your-github-handle",
  "favoriteColor": "#FF5E5B",
  "favoriteEmoji": "🦊",
  "message": "よろしくです！",
  "joinedAt": "2026-04-24"
}
```

これがトップページにカードで表示されます。好きな色が、カードの縁取りと光り方に反映されます。

### 自動チェック

PR を出すと自動のチェックが走り、`contributors.json` を8項目で確かめます。主な項目は次のとおりです。

- JSON として正しいか、全体が配列か
- 必須項目がそろっているか、空や空白だけになっていないか
- 色が `#RRGGBB`、日付が `YYYY-MM-DD` の形式か
- GitHub のハンドルが既存の人と重複していないか
- 絵文字が1文字か

ミスがあればチェックが失敗し、どの行の何がまずいのかを日本語で返します。これとは別に、サイト全体のビルドが通るかも確かめます。

## ここからは、作る側の話

同じような練習場を作りたい人向けの話です。参加するだけなら、読み飛ばして構いません。

### 技術スタック

| 何 | 使ったもの |
|----|-----------|
| フレームワーク | Next.js 16 (App Router、静的エクスポート) |
| UI | React 19 + Tailwind CSS v4 |
| 言語 | TypeScript |
| ホスティング | GitHub Pages（PR ごとのプレビューは Vercel） |
| CI（PR ごとに自動で動くチェック） | GitHub Actions |
| テスト | Vitest + Playwright |
| バリデーション | 自前の検証スクリプト（TypeScript） |

Next.js の静的エクスポートを使って全ページの HTML をビルド時に作っておくので、ファイルを置くだけで表示でき、プログラムを動かすサーバーは要りません。サーバー代はゼロです。main にマージされると、GitHub Actions がビルドして GitHub Pages に公開します。

最初は、ホスティングサービスの Vercel で公開していました。途中から GitHub Pages にも同じサイトを置いたため、どちらが正式な公開先なのか、私自身の案内もぶれていました。そこで正式な公開先を GitHub Pages に決め、Vercel は PR のプレビュー専用にしました。参加者は、マージ前にプレビューで自分のカードを確認できます。

### 練習場を壊されないための3層の守り

知らない人から PR が来る前提なので、`contributors.json` 以外は変えられないようにしています。

| 層 | 仕組み | 役割 |
|---|---|---|
| 1 | 変更されたファイルを検査するチェック（`guard-files`） | PR が `contributors.json` 以外を変えていたら、何がいけないかを日本語で返す |
| 2 | ファイルごとに承認者を決める設定（`CODEOWNERS`） | `contributors.json` 以外の変更には、オーナーの承認を必須にする |
| 3 | main への直接の変更を禁じる設定（ブランチ保護） | PR を経由すること、自動チェックが通ること、オーナーが承認することを、マージの条件にする |

1層目には落とし穴がありました。GitHub Actions のチェックは、PR が来ると、ワークフローというファイルに書いた手順のとおりに自動で動きます。普通の設定（`pull_request` イベント）では、PR に含まれるワークフローがそのまま使われます。そのため、PR でワークフロー自体を書き換えると、検査をすり抜けられてしまいます。これでは守りになりません。

そこで、PR 側ではなく main 側のワークフローで動く `pull_request_target` イベントに切り替えました。ただし、このイベントはリポジトリへの書き込みなどの権限を持ったまま動きます。危ないので、PR のコードは取り込み（checkout）も実行もしません。GitHub の API で変更されたファイルの一覧だけを取り、それで判定しています。

とはいえ、コードの改善を手伝ってくれる人を締め出したいわけではありません。そこで例外も用意しました。オーナーは、取り組んでほしい課題の Issue（課題や要望を書き込む場所）に `contribution-welcome` ラベルを付けておきます。PR の本文に `Closes #番号` と書いてその Issue を参照すれば、コードを変更していても `guard-files` を通過します。どの課題に取り組めるかは、Issue の一覧を見ればわかります。

### AI のレビューを、マージの判断に組み込む

PR のレビューには CodeRabbit（AI のコードレビューサービス）を使い、日本語でコメントさせています。ただ、レビューのコメントを読むだけでは、自分の PR を直す必要があるのかが、初心者にはわかりにくいものです。レビューの結果は、GitHub Actions でラベルに変換するようにしました。

- `ai:approved`（問題なし）
- `ai:approved-with-warnings`（注意点あり）
- `ai:changes-requested`（要修正）

要修正のときは `do-not-merge` ラベルも付けます。このラベルが付いている間は、ラベルの有無を確かめる `merge-guard` というチェックが失敗し、マージできません。

ひとつ誤算もありました。CodeRabbit は OSS なら無料で使えますが、スターが10未満のリポジトリには自動でレビューしません。この練習場はまだスターが少ないので、今はレビューを PR ごとに手動で起動しています。スターが増えれば、自動レビューに戻ります。

### テストは、わざと壊して確かめた

Vitest のユニットテストが179件、ブラウザで実際に画面を操作して確かめる E2E テスト（Playwright を使用）が16件あります。E2E では、チュートリアルの画像12枚がすべて読み込まれることと、画面に404やコンソールエラーが出ないことも確かめています。

テストを足したときは、修正前のコードに戻したり画像を1枚消したりして、テストがちゃんと失敗することも確かめました。修正前でも通ってしまうテストは、何も守っていないからです。

### 開発の進め方

機能を足すたびに、要件 → 設計 → タスク分解 → 実装の順に進め、各段階で文書を書いて、承認してから次に進みました。手間は増えますが、要件の段階で「何を変えて、何を変えないか」を決めておくと、実装中に迷いにくくなります。

技術的な判断は ADR（Architecture Decision Record。決めたことと、その理由を残す文書）に残しています。公開先の切り替えや、`pull_request_target` を使う理由など、今は11本あります。あとから「なんでこうしたんだっけ」となったとき、自分を助けてくれます。
